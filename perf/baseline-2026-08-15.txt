[5]-[8] Algeff 对比列（A7 批 4 复测，2026-08；对照 pdr.md §16 性能预期表）
--------------------------------------------------------------------------------
对比方式：等负载同参数双对比项（原生参照臂与 Algeff 臂在同一 bench 文件内测量，
同 setup、同 runtime 线程池配置、同服务端实现），
对比百分比 = Algeff 中位 / 原生中位 × 100%。

批 4 背景：A2 批 4 合并 D17（can_parallel=true 时 Fork 真并行：spawn_blocking × 2
+ current-thread runtime 驱动，执行器经 Arc<Mutex> 共享）。批 3（D14 顺序 Fork）
数据保留为「D14 顺序基线」历史对照行。批 3 预期 D17 并行后 parallel_reads 回归
pdr §16 ~100%；实测未达成，诊断见各条归因与文末「新增已知限制（批 4）」。

[5] algeff_echo: tokio_native_100conns_x1rtt_1KB vs algeff_100conns_x1rtt_1KB
    场景:   本地 TCP echo（127.0.0.1），每测量样本 100 连接 × 每连接 1 次
             1KB 往返（pdr.md §16「网络 Echo（无共享资源）」）
    负载说明: A4 资源线性（同一资源 Write 恰好消费一次）使批 2 的「100 连接 ×
             每连接 1000 往返」不可表达（第 2 个往返即 Err(InvalidInput)，见
             execution_axioms.rs::exec_A4_linearity_runtime）——CTO 裁决改为
             等负载双对比项（100 连接 × 1 往返）。批 2 的 100×1000 原生基线
             保留为历史参照列，不可与 Algeff 直接等比。
    参数:   sample_size=10, warm_up=50ms, measurement_time=100ms
            （每样本 ~1 iter；Windows 端口池约束限制测量窗口，见已知限制）
    批 4:  原生 [27.485 ms 27.771 ms 28.064 ms]（中位 27.771 ms）
           Algeff [28.269 ms 28.624 ms 28.983 ms]（中位 28.624 ms）
           对比 103.1%（pdr 预期 ~103%）
    历史:  （D14 顺序基线，批 3）原生 33.193 ms / Algeff 33.195 ms = 100.0%
    归因:   echo 无 Fork（单链 Sequential），与 D17 无关；顺带复测确认无回归
            （103.1% vs 批 3 100.0%，在每样本 1 iter 的 ±10% 噪声内，见批 3 备注）。

[6] algeff_parallel_reads: tokio_native_10x1MB vs algeff_fork10_x1MB
    场景:   并行读 10 个不同文件（各 1MB，零冲突，pdr.md §16「并行读取 10 个
             不同文件」）
    参数:   sample_size=10, measurement_time=3s
    批 4:  原生 [3.1010 ms 3.2327 ms 3.3875 ms]（中位 3.2327 ms）
           Algeff [11.095 ms 11.837 ms 12.460 ms]（中位 11.837 ms）
           对比 366.2%（pdr 预期 ~100%）
    历史:  （D14 顺序基线，批 3）原生 4.0102 ms / Algeff 13.635 ms = 340.0%
    归因:   D17 并行路径**已触发**（10 文件零冲突 → can_parallel=true →
            run_fork_parallel，分支线程并发），但读仍串行化——执行器互斥锁
            （`ExecAccess::Shared` 的 `Arc<Mutex<SendExecutor>>`）在 `exec_via`
            中对整个 `execute`（含物理 IO await）持锁，跨分支所有 Syscall
            串行通过该锁；逐 Fork 节点 spawn_blocking + current-thread runtime
            创建开销进一步抵消收益。实测 366% 与批 3 340% 无实质差异。
            锁边界收窄（物理 IO 移出锁外）属 A2 域（runtime.rs），本批不改。
    bench 变更: 批 4 实测发现 D17 并行分支各自从父 `next_fd` 克隆分配 fd 号，
            而共享执行器 `files` 映射以 fd 为键 → 分支内 Open 互相覆盖（读错
            文件/EOF，功能断言 10MB 失败）。故 Algeff 臂改为父 registry 顺序
            预开 10 文件、Fork 内每叶仅 Read→Close（被测负载不变，见
            benches/algeff_parallel_reads.rs 头注释）。复跑两次稳定：
            366.2% / 383.6%。

[7] algeff_shared_read: tokio_native_8tasks_8MB vs algeff_fork8_shared_8MB
    场景:   8 任务并发读同一 8MB 文件（只读共享，pdr.md §16「并行读取同一文件」）
    参数:   sample_size=10, measurement_time=3s
    批 4:  原生 [1.4618 ms 1.5036 ms 1.5547 ms]（中位 1.5036 ms）
           Algeff [8.2219 ms 8.5845 ms 8.9119 ms]（中位 8.5845 ms）
           对比 570.9%（pdr 预期 ~100%）
    历史:  （D14 顺序基线，批 3）原生 2.0848 ms / Algeff 6.4120 ms = 307.6%
    归因:   读-读冲突矩阵兼容（can_parallel=true）→ D17 并行路径触发，但读
            无并行收益：执行器互斥锁串行化全部 Syscall（同 [6]）+ 同一 fd
            游标读共用 `files[fd]` 文件互斥锁与游标（op_read 按序推进，即使
            锁边界收窄也不并行，需位置读原语）。spawn/runtime 创建开销叠加，
            实测 8.58ms 反超 D14 顺序基线（6.41ms）——D17 并行对同 fd 游标读
            是纯损失。诚实数据，不修饰。

[8] algeff_append: tokio_native_10tasks_x32KB vs algeff_serial_10tasks_x32KB
    场景:   10 任务追加同一文件（每任务 32 × 1KB；pdr.md §16「并行追加同一文件」）
    参数:   sample_size=10, measurement_time=3s
    批 4:  原生 [5.9324 ms 6.0947 ms 6.2529 ms]（中位 6.0947 ms）
           Algeff [1.4344 ms 1.4814 ms 1.5455 ms]（中位 1.4814 ms）
           对比 24.3%（pdr 预期 ~100%）
    历史:  （D14 顺序基线，批 3）原生 6.7828 ms / Algeff 1.9943 ms = 29.4%
    归因:   append 走 D6 默认串行路径（10 任务顺序 Open{append}+Write+Close，
            路径资源声明 AppendOnly 模式，CTO 批准），与 D17 无关；小负载下
            串行追加（1.48 ms）显著快于原生 10 路并行追加（6.09 ms）——
            串行默认的诚实数据。原生臂含每任务 flush()，Algeff 臂不 flush
            （小量不对称，如实记录，批 3 同款）。opt-in 并行
            （can_parallel_with append_order_insensitive）留待后续基准驱动。

新增已知限制（批 4）：
- parallel_reads/shared_read 的 D17 并行路径已被触发（冲突矩阵判定 + 线程并发），
  但读不并行：执行器互斥锁在 `exec_via` 中对整个 execute（含物理 IO await）
  持锁，跨分支 Syscall 全部串行。归因属 A2 域（runtime.rs `exec_via` 锁边界），
  A7 不改；待 A2 将锁边界收窄到执行器内部状态访问（物理 IO 移出锁外）后复测，
  目标回归 pdr §16 ~100%。
- shared_read 即使锁边界收窄也不可达 ~100%：同 fd 游标读共用文件互斥锁与游标，
  需要位置读（Seek+Read 跨分支原子化或位置读 DataOp）——执行器层（A5 域）待办。
- parallel_reads bench 蓝图因 D17 分支 fd 分配碰撞改为「顺序预开 + Fork 读」
  （fd 冲突根因：并行分支从相同 next_fd 克隆分配，共享执行器 fd 键控映射覆盖；
  属 runtime/执行器层设计约束，见 benches/algeff_parallel_reads.rs 头注释）。
- echo/append 与 D17 无关，顺带确认无回归（103.1% / 24.3%，均处批 3 噪声带）。
